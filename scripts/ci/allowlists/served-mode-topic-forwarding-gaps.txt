# served-mode-topic-forwarding allowlist — Topic* broker-topic consts with
# a real frontend `useEventStream(...)` subscriber that are NOT forwarded
# by core/serve/wsstream.go's passthroughTopics.
#
# Enforced by scripts/ci/check-served-mode-topic-forwarding.sh.
# Discovery: wsstream_topics_parity_test.go's header (connector-lifecycle-
# truth-01PMZ303 UNIT-8 / PR #336 review MUST FIX 1). Cross-referencing
# every `Topic* = "..."` Go const's declaring file against
# `useEventStream(...)` call sites in frontend/src surfaced FIVE such
# topics missing from passthroughTopics; mcp:health-changed was the sixth
# and is now fixed (it is forwarded, not allowlisted here). This file
# freezes the remaining five so a served-mode workbench silently missing
# an event they DO fire is a known, tracked gap — and so that check-
# served-mode-topic-forwarding.sh fails loudly on a NEW topic in this
# shape rather than letting it join the backlog unnoticed.
#
# Each of the five needs the SAME two-part disposition MUST FIX 1
# required for mcp:health-changed: (1) a passthroughTopics /
# SERVED_STREAM_TOPICS entry, AND (2) a session-scoping decision — does
# the payload carry a session id D-705's fail-closed filter
# (core/serve/wsstream.go's frameFor) can key on, or does it need a
# processWideTopics exemption the way TopicMigrationDriftDetected and
# mcp.TopicMCPHealthChanged both do? That is real per-topic research,
# not a mechanical fix, and out of scope for the PR that added this gate
# (fix/z303-mcp-health-truth) — tracked here as a candidate for its own
# follow-up mission instead of a rushed, unresearched disposition of four
# unrelated topics.
#
# Format: one double-quoted topic VALUE (not the Go identifier) per line,
# preceded by a comment giving the date, the const's
# <package-import-path>.<Identifier>, and the blocker + owner (never
# "we'll get to it" — see CLAUDE.md's "Release ritual: unwired sweep" /
# "Rules").
