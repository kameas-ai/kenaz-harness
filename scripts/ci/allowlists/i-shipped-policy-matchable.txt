# G-4 — shipped-policy-matchable class (kitty-specs/trust-surfaces-that-
# fire-01PMZ202 spec.md §G-4, WP18).
#
# Enforced by scripts/ci/check-shipped-policy-matchable.sh /
# scripts/ci/cmd/checkpolicymatch. For every `.cedar` file under
# core/policy/cedar/policies/, for every rule's action X: (a) X has a
# non-test evaluator that calls .Evaluate(; (b) a production UID builder
# reachable from that evaluator emits the rule's declared resource entity
# type; (c) that evaluator populates every context key the rule's
# when/unless clause reads. See main.go's header for the full design
# (this is the gate that would have caught F24 — the shipped filesystem-
# hardening template whose forbid rules were unmatchable for three
# independent reasons at once, fixed by WP12).
#
# THIS GATE'S ALLOWLIST IS DELIBERATELY MINIMAL, NOT A CASUAL ESCAPE
# HATCH — see main.go's header ("A DELIBERATELY TINY ALLOWLIST") for the
# full reasoning. Format: one line per violation, copied verbatim from
# the gate's stderr, followed by a `#` comment carrying the DATE, the
# BLOCKER, and the change that will delete the line. Entries shrink
# monotonically — a line that no longer matches a real violation is
# STALE and fails the gate.
#
# ============================================================
# 2026-09-12 — this gate's introduction. ONE finding, already
# investigated (not guessed):
# ============================================================
#
# default_acp_policy.cedar's `acp_receive` permit/forbid rules
# (including "forbid acp_receive from revoked peers" — the belt-and-
# suspenders safety rule the file's own header calls out) have NO
# evaluator anywhere in production. Confirmed by hand:
#   - `/usr/bin/grep -rn ActionACPReceive core/` (excluding _test.go)
#     returns only its own declaration + doc comment in types.go.
#   - No `ACP_Receive` function exists anywhere under core/ — only two
#     comments describing one that was apparently never built:
#     core/rpc/api.go:3372 ("acp_receive gates actually enforce
#     policy") and core/rpc/views/acp/acp.go:654 ("attrs is the context
#     map built by ACP_Dispatch / ACP_Receive").
#   - By contrast, `acp_send` (the sibling action in the SAME file) IS
#     genuinely wired end to end — ACP_Dispatch (acp.go) calls
#     a.cedarEng.Check(...), which is EngineAdapter.Check's generic
#     Evaluate(+ACPEnvelopeUID) wrapper — confirmed as a true negative
#     by this gate's own calibration run before this file was seeded.
#
# Net effect: inbound ACP envelope handling is not gated by Cedar today.
# A revoked peer's inbound envelopes are not denied by the rule that
# exists specifically to deny them — the exact "silent broken promise"
# shape this whole gate class exists to end, just on the receive side
# instead of the send side.
#
# Blocker: building the real ACP_Receive gate call is a genuine
# feature/security task (understand the ACP receive pipeline, decide
# where in it the Cedar check belongs, wire CheckACPReceive-equivalent
# the same way ACP_Dispatch wires acp_send) — out of scope for this
# gate-authoring change, which introduces the DETECTOR, not the fix.
# Owner: whoever next touches core/rpc/views/acp/ (ACP receive-path
# work) should wire this and delete all three lines below in the same
# change, or escalate if there's a reason inbound envelopes are
# intentionally ungated that this investigation didn't surface.
